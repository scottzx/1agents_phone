## 0. 产品故事母版

今天的旅行 AI 很擅长生成一份计划，但一趟 10 天、15 天的长途自驾不会按照生成那一刻的世界运行。道路会变、天气会变、预约会变、同行人会变，而酒店、机票和用户自己的承诺仍然存在。

疆行从出发前建立 Trip Agent Graph，把路线、时间、费用、承诺与成行条件组织成一趟真正可执行的旅行；旅途中，当现实发生变化，Agent 传播影响、比较方案，并在用户确认后以最小扰动恢复成行；旅行结束后，真实轨迹与决策沉淀为用户可控的记忆，进入下一趟旅行。

**规划一趟新疆自驾并不难。难的是第 6 天，它还成立吗？**

**疆行，让长途自驾，持续成行。**

## 1. 产品定义

### 1.1 名称与口号

- 产品名：**疆行**
- 口号：**让长途自驾，持续成行。**

### 1.2 正式定义

疆行是一款面向长途自驾的旅行 Agent。它从出发前建立成行计划，在旅途中持续维护计划，在旅行结束后沉淀真实经历，让经验进入下一趟旅程。

它不是「新疆旅游攻略 AI」，也不是「AI 路线规划器」。

三个词定义完整生命周期：

**建立 → 维护 → 沉淀**

对应同一个 Trip Agent Graph 的三幕：

| 幕 | 内部名 | 回答的问题 |
|---|---|---|
| 建立成行计划 | BUILD | 这趟旅行怎样才能成立？ |
| 持续成行 | MAINTAIN | 现实发生变化之后，它怎样继续成立？ |
| 旅程沉淀 | LEARN | 这次实际发生的旅行，给下一趟留下了什么？ |

然后进入新的 Graph：北疆 Graph → 完成 → 南疆 Graph → 完成 → 西藏 Graph……

于是产品真正的「持续」是：

> **Build → Maintain → Learn → Build → Maintain → Learn…**

### 1.3 我们管理的对象

整个项目只围绕一个问题展开：

> **规划一趟新疆自驾并不难。难的是第 6 天，它还成立吗？**

因为一趟真正的长途旅行不是一张静态 itinerary，而是一组会被现实不断影响的**路线、时间、费用、承诺和成行条件**。

所以我们不是比谁更会生成 Plan。

我们管理的是：

# **Plan 在现实世界中的生命周期。**

### 1.4 竞争责任边界

不要做功能对照表。竞争不是 Feature，而是产品承担的责任不同。

| 角色 | 负责什么 |
|---|---|
| 地图 | 怎么走 |
| OTA | 怎么买 |
| 旅行 AI | 怎么玩 |
| **疆行** | **让已经决定的旅程持续走得成** |

二维定位：

- 横轴：**Plan → Operate**
- 纵轴：**Session → Journey**

传统 LLM / AI itinerary 偏左上（一次会话生成计划）。地图偏右，但主要解决即时导航执行。OTA 拥有长期订单，核心仍是交易和行程服务。疆行占 **Operate × Journey**：跨越整个旅程生命周期持续维护状态。

## 2. 背景与机会

传统旅行产品擅长路线查询、订单预订、导航和单点问答。一趟新疆自驾跨越数天、多个城市、多个外部服务与不断变化的现实条件。真正困难的不是「查到一个答案」或「生成一张日程」，而是：

- 证、约、路、油、网、人同时约束同一条线，而且会过期；
- 一次道路、天气、预约或时间变化会传播到酒店、补给、日照和后续数天；
- 用户已经订了酒店、买了票、跟朋友约好、跑了五天，不能轻易推翻整份计划；
- 修改计划后，路书、日历和提醒可能部分成功，难以追溯与撤销；
- 新疆长距离与弱网场景要求关键资料随时可离线读取；
- 上一趟真实决策没有进入下一趟规划，每次都从零认识这个用户。

Agent 的价值因此不在新增一个查询入口，而在于长期维护同一份 Plan 的成行状态：检查什么被破坏，用最小改动恢复成行，并把真实决策沉淀为下一趟 Graph 的输入。

## 3. 产品目标与非目标

### 3.1 产品目标

1. **BUILD**：从用户目标与已有承诺建立一份可成行的 Plan，而不是一张按天罗列的攻略。
2. **MAINTAIN**：现实变化后，先判断现有 Graph 什么被破坏，再用最小扰动恢复成行。
3. **执行闭环**：用户确认后的变更可预览、提交、读回验证、出回执、撤销。
4. **LEARN**：对照 Plan 与 Reality，从真实决策产生候选记忆，由用户确认后进入下一趟 Graph。
5. **跨 Graph 记忆**：每趟旅行拥有独立 Graph；用户拥有跨 Graph 的可控 Memory。
6. **弱网可用**：无网时保留今天/明天行程、订单凭证、联系人和最近一次可信计划。

### 3.2 非目标

- 不做旅游社区、OTA、营地商城或服务商管理平台；
- 不在 App 内完成支付、租车履约、保险销售或商家评价闭环；
- 不替用户提交官方预约、边防申请或外部交易；
- 不直接控制车辆，不参与自动驾驶决策；
- 不替代交警、道路管理、医疗、维修、保险等专业判断；
- 不把聊天当作产品本身，不把「AI 生成旅行视频」当作 Agent 核心；
- 不承诺 iOS 后台永久运行 Agent；
- 比赛版不迁移、不运行、不集成 TREK 代码、服务或视觉资产。

## 4. 目标用户与核心任务

### 4.1 首要用户

自行组织新疆长途自驾的个人、伴侣或家庭旅行组织者。他们会跨多个平台做攻略、购买机票与酒店、租车、保存截图，并在途中承担全队行程协调责任。

### 4.2 核心任务

| 阶段 | 用户要完成的事 | 产品必须交付的结果 |
|---|---|---|
| BUILD | 说出目标，导入已有承诺 | 一份带成行状态的 Plan + Trip Agent Graph |
| MAINTAIN | 报告或发现现实变化 | 冲突原因、最小扰动方案、确认后的恢复成行 |
| 执行 | 确认某一方案 | ChangeSet、写入、读回验证、回执、Undo |
| 弱网 | 出城后仍要看今天怎么走 | 离线路书、凭证、联系人、最近可信快照 |
| LEARN | 旅行结束，准备下一趟 | Plan vs Actual、候选 Memory、下一趟 Graph 可沿用 |

## 5. 产品原则

1. **成行状态优先于聊天记录。** 聊天、语音和截图只是输入。用户看到的始终是这趟旅行现在能不能成立。
2. **建立的是可成行 Plan，不是攻略。** Plan 必须同时包含时间、路线、费用、承诺和成行条件。
3. **承诺优先于推荐。** 先识别不可随意更改的机票、住宿、租车和同行人约定，再谈路线。
4. **最小扰动恢复成行。** 优化目标不是 Find another route，而是在满足新约束的情况下尽可能保留已确认 Commitment。
5. **建议必须带影响。** 比较方案时同时看时间、里程、费用、酒店影响、用户偏好和已有承诺。
6. **Agent 的任务不是给建议，而是完成并证明这次改变。** Preview → Confirm → Commit → Read-back → Receipt → Undo。
7. **记忆必须由用户拥有。** 从真实决策产生候选记忆，用户选择保存 / 修改 / 忽略；展示来源、适用范围，允许暂停和遗忘。
8. **安全动作由用户触发。** 导航、电话、短信、报警和外部交易都需要用户最终确认。
9. **本地为主、网络为能力。** 旅程和记忆不依赖自建服务器；模型、搜索、天气和地图可按需联网。

## 6. 三幕需求

### 6.1 BUILD｜建立成行计划

**用户可以说：**

> 「我想两个人自驾新疆 12 天，不想太赶，预算两万五。」

**疆行最终建立的不能只是：**

Day 1 去哪 / Day 2 去哪 / Day 3 去哪

**必须建立：一份可成行的 Plan。** 它由五类对象构成。

| 对象 | 必须覆盖的内容 |
|---|---|
| Time | 旅行日期、每日驾驶时长、固定到达时间、营业时间、预约提前量、通行窗口、日照余量 |
| Route | 每日路线、公里数、驾驶时间、油站/充电、休息点、弱网路段、替代路线 |
| Cost | 预算、已支付成本、预计油费/住宿/门票，以及未来改变计划产生的变更成本 |
| Commitment | 已经订好的酒店、门票、航班、同行人固定时间，以及用户明确不愿意破坏的安排 |
| Constraint | 预约、证件、道路开放、天气、车辆条件、装备、同行人状态、离线准备 |

用户最终看到的不是「这是你的新疆攻略」，而是成行状态板：

```text
北疆 12 天
成行状态：有条件成行

✓ 主路线成立
✓ 预算 ¥25,000 内
✓ 9/11 晚住宿已确认
△ 独库预约待完成
△ 离线地图待下载
△ 同行人 A 边防资料待确认
```

成行状态枚举：

| 状态 | 含义 | 用户看到什么 |
|---|---|---|
| 可成行 | 主路线、关键承诺与阻塞项均满足 | 可以按计划走 |
| 有条件成行 | 主路线成立，但仍有待完成条件 | 列出待办，不假装已经没问题 |
| 暂不可成行 | 存在阻塞项，现有 Plan 不再成立 | 说明被破坏的对象，进入 Recovery |
| 信息不足 | 关键事实无法确认 | 标注「无法确认」，保留原计划，不猜测 |

BUILD 完成的技术标志：

**Trip Agent Graph Established**

BUILD 的验收：

- 输出不是按天攻略列表，而是五类对象齐全的 Plan；
- 首页展示成行状态，而不是聊天摘要；
- 已确认 Commitment 被显式标记，后续 Recovery 默认保护它们；
- 待完成条件以阻塞项/待办呈现，不把「有条件成行」写成「可成行」。

### 6.2 MAINTAIN｜持续成行（Hero Capability）

这是整个项目最重要的能力，比赛投入约 50% 的 Demo / UI / 视频时间。

Day 6，现实发生变化。可能是：道路规则变化、预约失败、暴雨、ETA 延迟、同行人临时改变、景区关闭。

这时候疆行不是「重新生成一份新疆攻略」，而是先检查现有 Graph：

1. **什么被破坏了？**
2. **如何用最小的改动恢复成行？**

正式设计原则：

# **最小扰动恢复成行**

英文内部名：**Minimum-disruption Recovery**

用户已经订了酒店、买了票、跟朋友约好、跑了五天。Agent 不应该轻易推翻整个计划。优化目标是：

> **在满足新约束的情况下，尽可能保留已经确认的 Commitment。**

MAINTAIN 标准流程：

```text
新事实进入
  → Graph 传播（Time / Route / Cost / Commitment / Constraint）
  → 成行状态变化（可成行 → 暂不可成行）
  → 列出阻塞项
  → 生成至少两个 Recovery Plan
  → 按时间 / 里程 / 费用 / 酒店影响 / 偏好 / 已有承诺比较
  → Preview ChangeSet
  → 用户确认
  → Commit
  → Read-back Verification
  → Receipt + Undo
  → 已恢复成行
```

Recovery 方案比较维度（全部展示，不可只比路线）：

- 时间（出发、到达、日照余量）
- 里程与驾驶时长
- 费用与变更成本
- 酒店 / 订单等 Commitment 是否被破坏
- 用户已确认偏好
- 已跑天数与后续日程扰动范围

MAINTAIN 的验收：

- 一次变化必须能指出被破坏的 Graph 对象，而不是只说「建议改线」；
- 至少给出两个可比较的 Recovery Plan；
- 默认保护已确认 Commitment；若必须破坏，ChangeSet 里显式标红；
- 用户未确认前不得写入路书、提醒或外部系统对象；
- 确认后必须走完 Preview → Commit → Verify → Receipt → Undo。

### 6.3 LEARN｜旅程沉淀

照片、视频、足迹可以做，但它们是**产品体验出口**，不是 Agent 核心。

真正重要的是：

# **Plan 和 Reality 的差异。**

出发前疆行知道用户计划怎么走。旅行完成后它知道用户实际上怎么走。

示例：

| 计划 | 实际 | 可提出的候选记忆 |
|---|---|---|
| 连续驾驶 7h 用户认为可以接受 | 超过 5.5h 两次主动增加休息 | 长途日超过 5.5h 通常希望休息一次 |
| 夜路可以接受 | 两次选择都提前出发而不是夜驾 | 优先保证日落余量，即使需要更早出发 |

产品话术必须是候选，不是自动生效：

> 这趟旅程发现一个可能值得保存的偏好：  
> 长途自驾中，优先保证日落余量，即使需要更早出发。  
> 来源：Day 6 独库决策 / Day 9 ×× 决策  
> **保存 / 修改 / 忽略**

Memory 不是「AI 自动记住用户喜欢什么」，而是：

# **从真实决策中产生候选记忆，并由用户确认。**

然后自然进入下一趟 Graph。用户说「下次想走南疆」时，疆行不是重新认识这个用户。新的 South Xinjiang Trip Agent Graph 开始 Build，但上一趟经过用户确认的记忆可以参与：

- 上次你连续驾驶 5.5 小时后通常希望休息一次，要继续沿用吗？
- 上次你选择优先保证通行窗口而不是晚出发，要作为这次默认策略吗？
- 上次你偏好少换酒店，本次南疆线继续这样安排吗？

用户可以：**沿用 / 修改 / 本次不用**。

架构结论：

- 每趟旅行拥有**独立 Graph**；
- 用户拥有**跨 Graph 的可控 Memory**。

LEARN 的验收：

- 必须能对照至少一组 Plan vs Actual，而不是只生成相册或短片；
- 候选记忆必须引用真实 decision / action ID；
- 未确认的候选不得自动写入下一趟 Graph；
- 下一趟 BUILD 读取的是用户已确认记忆，并提供沿用 / 修改 / 本次不用。

## 7. Trip Agent Graph

Trip Agent Graph 是整个产品的技术骨架。主 PPT 不需要出现十几个 Agent 技术词，重点只讲这个。

它是一个随着旅程进行不断变化、可被 Agent 推理和操作的旅行状态图。

### 7.1 节点类型

| 节点 | 职责 |
|---|---|
| Route | 路线与空间关系 |
| Time | 时间窗口、ETA、固定时间点 |
| Cost | 预算、实际成本、变更成本 |
| Commitment | 酒店、订单、同行人约定 |
| Constraint | 道路、预约、天气、驾驶偏好 |
| Dynamic Fact | 不断变化的现实世界状态 |
| Evidence | 每一个事实从哪里来 |
| Action | 可以被执行的修改 |

### 7.2 三幕对 Graph 的操作

| 幕 | 对 Graph 做什么 |
|---|---|
| BUILD | 创建 Graph |
| MAINTAIN | 更新 Graph + 传播变化 + Recovery |
| LEARN | 总结 Graph + 产生候选 Memory |

### 7.3 传播要求

一个 Dynamic Fact 进入后，必须沿边传播，而不是只改当天。Hero Demo 的最小传播链：

```text
通行时间
  → ETA 冲突
  → 出发时间
  → 午餐
  → 日照余量
  → 酒店 ETA
  → Reminder
```

产品必须能回答评委那句：

> **一个变化，为什么会影响后面三天？**

### 7.4 护城河（三层，可替换模型与地图）

模型和高德都可以替换。真正逐渐积累的是：

1. **Trip Agent Graph Schema**：怎样表达真实旅行状态。
2. **Recovery Engine**：现实变化后怎样进行影响传播与最小扰动重排。
3. **Cross-trip Memory**：真实旅行决策怎样成为下一趟 Graph 的输入。

## 8. 信息架构

首页不是功能九宫格，也不是聊天窗口。它投影当前 Graph 的成行状态。

### 8.1 旅程首页 / 成行状态板

- 当前幕：BUILD / MAINTAIN / LEARN，以及旅行阶段（计划中、准备中、行驶中、已抵达、复盘中）；
- 成行状态：可成行 / 有条件成行 / 暂不可成行 / 信息不足；
- 今天与下一里程碑；
- 阻塞项与待完成条件；
- Agent 长期任务状态：运行、等待事件、等待用户、失败、已恢复；
- 新事实、影响范围、下一项待确认决策；
- 最近一次提交回执与撤销；
- 快捷输入：语音、相机、截图/文件。

### 8.2 路书时间轴（BUILD / MAINTAIN 共用）

- 按天组织地点、驾驶段、停留、住宿、补给与固定订单；
- 计划与实际可并列，延误可向未来传播；
- 候选、已确认、已取消状态清晰；
- 展示数据来源、更新时间和「为什么这样安排」；
- 显示本次计划使用了哪些已确认记忆。

### 8.3 证据与新事实入口

- 输入：照片、截图、PDF、链接、分享扩展、语音和手动录入；
- 输出：结构化 Dynamic Fact / Commitment / Constraint，带置信度、来源裁剪与冲突提示；
- 操作：确认、编辑、忽略、关联到某天；
- 原件保存在本地，结构化事实引用原件；
- 无法稳定提取时，退回用户手动选择和录入，不得用模型猜测伪装成官方事实。

### 8.4 Recovery 中心（MAINTAIN Hero）

- 展示「新事实 → 被破坏对象 → 受影响日期/订单」的传播链；
- 比较至少两个 Recovery Plan；
- 修改前展示 ChangeSet；确认后执行、验证并生成回执。

### 8.5 安全与离线包

- 今日/明日路线、坐标、订单凭证、住宿电话；
- 租车、保险、车辆信息；
- 健康卡、紧急联系人、常用应急电话；
- 数据新鲜度和最后更新时间；
- 电话、短信、导航和报警由用户最终触发。

### 8.6 足迹与复盘（LEARN 体验出口）

- 计划与实际路线、照片、语音、费用和临时事件；
- 生成每日小结和全程复盘；
- 区分被验证的偏好与被纠正的假设；
- 照片 / 短片 / 足迹可导出或分享，但不得替代 Plan vs Actual 与候选 Memory。

### 8.7 Memory Center

- 展示 Agent 认为它知道什么、为何知道、适用于何种场景；
- 支持确认、编辑、暂停、合并冲突、遗忘单条和清空某趟贡献；
- 以「来自 Day 6 独库决策 / Day 9 ×× 决策」等来源说明代替不可解释画像。

## 9. Agent 执行协议

Agent 的任务不是「给建议」，而是完成并证明这次改变。

### 9.1 标准闭环

1. **任务输入**：接收用户目标、截图、文档、位置、时间或外部事件。
2. **意图与约束理解**：识别目标、Commitment、Constraint 和安全边界。
3. **Graph 操作**：BUILD 时创建；MAINTAIN 时传播并生成 Recovery；LEARN 时对照并提出候选 Memory。
4. **能力调用**：视觉理解、文件工具、地图算路、天气、Calendar、Reminders、公开信息检索。
5. **结果预览**：结构化展示依据、方案比较和 ChangeSet。
6. **人工确认**：高影响动作由用户确认。
7. **提交与验证**：更新旅行包及系统对象，读回检查并生成回执。
8. **持续维护**：等待事件、从 checkpoint 恢复、复盘并提出候选记忆。

### 9.2 任务状态

`planned / running / waiting_event / waiting_user / paused / failed / completed / cancelled`

每个任务包含目标、当前阶段、checkpoint、输入实体版本、已处理事件 ID、下一唤醒条件、中间产物、待执行 ChangeSet、最近运行时间、失败原因与用户可见摘要。

### 9.3 iOS 恢复机制

执行入口包括前台用户动作、Share Extension、App Intents/Shortcuts、BGTask 的机会性刷新、本地通知响应和 App 前台恢复。App 不假装持续驻留后台，而是把长周期任务保存为可恢复状态，在事件触发后继续。

### 9.4 写入协议

1. 写入 `pending` 操作日志并记录预期 ChangeSet；
2. 保存修改前快照；
3. 原子写入旅行文件投影；
4. 用稳定外部映射 ID 更新 Calendar / Reminders；
5. 读取本地与系统对象验证；
6. 成功写入 `committed` 回执，失败写入 `failed` 与补偿状态；
7. Undo 生成新的反向操作，不删除历史；
8. App 恢复时扫描未终结操作并对账。

写操作接受 `operationId` 作为幂等键，并返回 ChangeSet、commit ID、状态和受影响实体。

## 10. 中长期记忆

### 10.1 生成规则

1. 一次临时选择只形成候选记忆，不自动升级为永久偏好。
2. 候选记忆必须引用真实 decision / action ID，并写明来源日期。
3. 明确声明高于模型推断；当前旅程显式约束高于长期记忆。
4. 高影响决策展示所用记忆，并提供覆盖入口。
5. 矛盾证据降低置信度并触发澄清。
6. 健康信息单独授权，不进入通用偏好。
7. 用户可导出、编辑、暂停、遗忘；删除后重建相关投影。

### 10.2 三层记忆

| 层级 | 内容 | 示例 | 生效方式 |
|---|---|---|---|
| L1 日常节律 | 餐饮、作息、休息和密度 | 城市休闲日晚起；长途日可 8:00 出发 | 当前旅程情境优先 |
| L2 出行方式 | 交通方式、驾驶与风险偏好 | 自驾优先；家庭远途不赶夜路 | 多次选择或明确确认 |
| L3 跨旅程经历 | 去过哪里、喜欢什么、要重复还是求新 | 重游喀纳斯但换季节；本次想避开同类路线 | 每次规划先判断 repeat / deepen / contrast / avoid |

### 10.3 记忆最小字段

`id、kind、value、scope、status、confidence、evidence、contradictions、createdAt、lastValidatedAt、expiresAt、userConfirmed`

状态流：`candidate → confirmed → reinforced`，也可进入 `contested / paused / forgotten`。

下一趟 Graph 只读取 `confirmed` 或 `reinforced`，并在 BUILD 时询问沿用 / 修改 / 本次不用。

## 11. 比赛版数据与工具

### 11.1 旅行包（Approach A）

```text
Trips/<trip-id>/
  manifest.json
  trip.json
  graph.json
  commitments.json
  itinerary.json
  tasks.json
  memories.json
  artifacts/
  journal/action-journal.jsonl
  journal/memory-journal.jsonl
  snapshots/<commit-id>/
  receipts/<commit-id>.json
  exports/
```

所有实体使用 `schemaVersion` 与稳定 ID。模型不直接编辑文件，只能通过受控 `trip-local` 工具读取和变更。

`graph.json` 是 Trip Agent Graph 的权威投影：Route / Time / Cost / Commitment / Constraint / Dynamic Fact / Evidence / Action。

### 11.2 核心工具契约

```text
trip-local trip show
trip-local artifact import
trip-local evidence confirm
trip-local graph evaluate
trip-local feasibility evaluate
trip-local change preview
trip-local change commit
trip-local change verify
trip-local change undo
trip-local memory propose
trip-local memory confirm
trip-local memory forget
trip-local export card
```

`graph evaluate` 负责：读入新事实、传播影响、输出被破坏对象、成行状态和 Recovery 候选。`feasibility evaluate` 输出可成行 / 有条件成行 / 暂不可成行 / 信息不足。

### 11.3 长期架构（Approach B）

赛后将旅行实体迁移到本地 SQLite TripStore，附件保留为文件；Agent 继续通过相同工具契约调用原生旅行 Offload，UI 订阅同一状态。比赛旅行包成为可移植交换格式，实体 ID、ChangeSet、日志语义与 ViewModel 保持兼容。

## 12. 比赛 Demo

PPT、HTML、视频必须讲同一个三章故事。不要各做一套。

### 12.1 章节 A：BUILD（20–30 秒）

用户：

> 「帮我规划一趟 12 天新疆自驾。」

快速建立成行计划。不需要耗时演示全部规划过程。

结束画面：北疆 12 天，成行状态为**有条件成行**或**可成行**，五类对象可见，Graph Established。

### 12.2 章节 B：Day 6 MAINTAIN（60–80 秒，Hero）

这是整个比赛核心小闭环。

**原状态**

计划明天进入独库。系统原来判断：**可成行**。

**新事实进入**

官方通行窗口 / 预约要求变化。地图重新计算 ETA。

**Graph 传播**

通行时间 → ETA 冲突 → 出发时间 → 午餐 → 日照余量 → 酒店 ETA → Reminder。

**状态变成**

**暂不可成行**。原因：2 个阻塞项。

**两个 Recovery Plan**

- A 提前出发。
- B 保留节奏、换候补路线。

比较时间、里程、费用、酒店影响、用户偏好、已有承诺。不是简单推荐。

**用户确认 A**

Preview ChangeSet → Commit Route / Roadbook / Reminder → Read-back Verification **3 / 3 verified** → Receipt + Undo → **已恢复成行**。

### 12.3 章节 C：LEARN / Next Trip（20–30 秒）

旅行完成。计划 vs 实际。照片可作为体验出口。提出候选 Memory。

用户：

> 「下一次想走南疆。」

出现：

> 是否沿用上次旅行的 3 个偏好？

画面结束。

### 12.4 错误分支

- 官方来源不可访问时显示「无法确认 / 信息不足」，保留原计划；
- 高德接口失败时回退到最近一次可信快照并标注更新时间；
- 没有官方预约接口时只给出入口和操作清单，不替用户提交；
- 截图无法稳定识别时要求用户手工补录。

任何失败都不得用模型猜测伪装成真实事实或执行成功。

## 13. 数据、隐私与安全

- 用户提供的截图、文档、健康卡和联系人默认保存在设备本地；
- 发送给用户选择的模型或外部 API 的内容必须在隐私说明中披露并最小化；
- 示例数据采用公开、模拟或已授权脱敏材料，标注来源、更新时间和适用边界；
- 位置、车辆、健康与联系人权限按需申请，可随时关闭；
- 高风险建议展示不确定性、依据、新鲜度和人工确认；
- 汽车场景不接入车辆安全控制，不提供自动驾驶决策；
- 紧急情况下只提供信息组织和快速入口，最终报警与导航由用户触发；
- 第三方模型、API、SDK、开源依赖、许可证和关键版本在提交材料中完整披露。

### 13.1 模型接入策略

产品不绑定单一模型。iagents_app / Minis 通过 Provider 抽象支持接入各类公有云模型，用户自行配置服务商、模型与凭证，并可根据能力、速度、价格和隐私要求切换。

比赛建议配置：

- **首选：阿里云百炼 Qwen3.8-Max Preview**，API 模型 ID 为 `qwen3.8-max-preview`。用于任务理解、长程规划、工具调用、截图/图片理解和结果解释；当前属于 Token Plan 提供的预览模型，正式提交需披露预览状态、调用接口、Credits 费用方式与版本替换风险。
- **备选：DeepSeek-V4-Pro**，API 模型 ID 为 `deepseek-v4-pro`。用于任务拆解、复杂推理、工具调用和结构化输出；其公有云 API 支持 Tool Calls，但模型输入以文本为主，处理截图时需配合独立视觉模型或本地 Vision Skill。

为保证 Demo 可复现，提交时冻结实际使用的模型 ID、接口类型、推理模式和关键参数；同时保留 Provider 可替换设计。模型只负责理解、规划和解释；地图算路、时间计算、Graph 传播、系统写入、媒体剪辑和结果验证由确定性工具完成。

## 14. 评测与验收

### 14.1 BUILD

- 输出五类对象齐全的可成行 Plan，而不是按天攻略；
- 成行状态可见，待办条件不会被写成「可成行」；
- 已确认 Commitment 进入 Graph，并在后续 Recovery 中被默认保护。

### 14.2 MAINTAIN / Agent 闭环

- 同一 `tripId` 跨调研、确认、写入和两次 App 重启继续；
- 一次新事实能指出被破坏对象，并传播到后续至少一天；
- 一次冲突影响路线、路书和提醒至少三个领域对象；
- 至少两个 Recovery Plan，并比较时间 / 费用 / Commitment / 偏好；
- 用户确认后，本地旅行包、Calendar 和 Reminders 均读回验证（Hero Demo 为 3 / 3 verified）。

### 14.3 可靠性

- 同一 `operationId` 重试不生成重复系统项；
- 任一步骤退出后可恢复并解释当前状态；
- Undo 通过反向操作恢复投影和系统对象；
- 无网时可查看今天/明天、关键凭证、联系人和最近路线快照。

### 14.4 LEARN / 记忆

- 候选记忆引用真实 decision / action ID；
- 下一趟旅行读取已确认记忆，而非固定文案；
- 用户可查看来源、修改、暂停、遗忘，或选择本次不用；
- 情境冲突时询问用户，不盲目套用。

### 14.5 Demo 完成度

- 90–150 秒视频按三章讲清 BUILD → Day 6 MAINTAIN → LEARN / Next Trip；
- Hero 段必须看到：可成行 → 暂不可成行 → 两方案 → 3 / 3 verified → 已恢复成行；
- 提供截图、操作日志、提交回执与故障恢复证据；
- 路演、Demo、样例数据和运行说明互相一致。
