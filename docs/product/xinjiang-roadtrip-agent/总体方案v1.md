我建议把“疆行”的整体设计正式收敛成下面这版。

# 一、项目的最高层定义

## 项目名称

# **疆行**

### **让长途自驾，持续成行。**

它不是“新疆旅游攻略 AI”，也不是“AI 路线规划器”。

正式产品定义可以定成：

> **疆行是一款面向长途自驾的旅行 Agent。它从出发前建立成行计划，在旅途中持续维护计划，在旅行结束后沉淀真实经历，让经验进入下一趟旅程。**

这里最重要的是三个词：

**建立 → 维护 → 沉淀**

它们对应的是同一个 Trip Agent Graph 的完整生命周期。

---

# 二、整个项目只围绕一个问题展开

核心问题继续保留：

# **规划一趟新疆自驾并不难。**
# **难的是第 6 天，它还成立吗？**

这句话承担“为什么需要疆行”。

而答案就是：

> 因为一趟真正的长途旅行不是一张静态 itinerary，而是一组会被现实不断影响的**路线、时间、费用、承诺和成行条件**。

所以我们不是比谁更会生成 Plan。

我们管理的是：

# **Plan 在现实世界中的生命周期。**

这是整个项目最根本的判断。

---

# 三、产品完整大闭环正式定成三幕

我建议以后不再说“规划 / 动态调整 / 总结”这么普通。

统一叫：

# **BUILD → MAINTAIN → LEARN**

分别对应：

## 01 BUILD｜建立成行计划

回答：

> **这趟旅行怎样才能成立？**

## 02 MAINTAIN｜持续成行

回答：

> **现实发生变化之后，它怎样继续成立？**

## 03 LEARN｜旅程沉淀

回答：

> **这次实际发生的旅行，给下一趟留下了什么？**

然后进入新的 Graph：

**北疆 Graph → 完成 → 南疆 Graph → 完成 → 西藏 Graph……**

于是它实际上形成一个长期循环：

> **Build → Maintain → Learn → Build → Maintain → Learn…**

这才是疆行真正意义上的“持续”。

# 四、第一幕：BUILD 不能做成普通 AI 行程生成

这是之后 Demo 和 PPT 必须非常克制的地方。

用户当然可以说：

> “我想两个人自驾新疆 12 天，不想太赶，预算两万五。”

但疆行最终建立的不能只是一张：

Day 1 去哪  
Day 2 去哪  
Day 3 去哪

而是：

# **一份可成行的 Plan**

它由五类东西构成。

### 1. 时间 Time

旅行日期、每日驾驶时长、固定到达时间、营业时间、预约提前量、通行窗口、日照余量。

### 2. 路线 Route

每日路线、公里数、驾驶时间、油站/充电、休息点、弱网路段、替代路线。

### 3. 费用 Cost

预算、已支付成本、预计油费/住宿/门票，以及未来改变计划产生的变更成本。

### 4. 承诺 Commitment

已经订好的酒店、门票、航班、同行人固定时间，以及用户明确不愿意破坏的安排。

### 5. 成行条件 Constraint

预约、证件、道路开放、天气、车辆条件、装备、同行人状态、离线准备等。

于是用户最终看到的不是：

> “这是你的新疆攻略。”

而应该是：

## **北疆 12 天**

**成行状态：有条件成行**

✓ 主路线成立  
✓ 预算 ¥25,000 内  
✓ 9/11 晚住宿已确认  
△ 独库预约待完成  
△ 离线地图待下载  
△ 同行人 A 边防资料待确认

这才有疆行的产品味。

# 五、第二幕：MAINTAIN 是整个项目的 Hero Capability

这部分继续作为整个比赛最精彩的 50% 左右。

因为真正的差异就在这里。

## Day 6

现实发生变化。

可能是：

道路规则变化  
预约失败  
暴雨  
ETA 延迟  
同行人临时改变  
景区关闭

这时候疆行不是：

> “重新生成一份新疆攻略。”

而是先检查现有 Graph：

> **什么被破坏了？**

然后：

> **如何用最小的改动恢复成行？**

这里我建议我们正式再锁定一个设计原则：

# **最小扰动恢复成行**

英文内部可以叫：

**Minimum-disruption Recovery**

这是非常符合旅行实际的。

用户已经：

订了酒店，  
买了票，  
跟朋友约好了，  
跑了五天。

Agent 不应该轻易推翻整个计划。

所以优化目标不是单纯：

> Find another route.

而是：

> **在满足新约束的情况下，尽可能保留已经确认的 Commitment。**

这个思想会让疆行明显比“动态行程规划”深一层。

# 七、第三幕：LEARN 不只是“AI 生成旅行视频”

这里也正式定调。

照片、视频、足迹可以做。

但它们是**产品体验出口**，不是 Agent 核心。

真正重要的是：

# **Plan 和 Reality 的差异。**

出发前疆行知道：

> 用户计划怎么走。

旅行完成之后它知道：

> 用户实际上怎么走。

这是非常有价值的东西。

---

比如：

计划：

连续驾驶 7h 用户认为可以接受。

实际：

超过 5.5h 两次主动增加休息。

计划：

用户觉得夜路可以接受。

实际：

两次遇到选择，都选择提前出发而不是夜驾。

于是疆行可以提出：

> **这趟旅程发现一个可能值得保存的偏好：**
>
> 长途自驾中，优先保证日落余量，即使需要更早出发。
>
> 来源：Day 6 独库决策 / Day 9 ×× 决策
>
> 保存 / 修改 / 忽略

这样 Memory 就不是：

> “AI 自动记住用户喜欢什么。”

而是：

# **从真实决策中产生候选记忆，并由用户确认。**

这个可信度会高很多。

# 八、然后自然进入下一趟 Graph

这就是刚才你提出的非常重要的一点。

用户回来之后说：

> “下次想走南疆。”

疆行不是重新认识这个用户。

新的 **South Xinjiang Trip Agent Graph** 开始 Build。

但是上一趟经过用户确认的记忆可以参与：

> 上次你连续驾驶 5.5 小时后通常希望休息一次，要继续沿用吗？

> 上次你选择优先保证通行窗口而不是晚出发，要作为这次默认策略吗？

> 上次你偏好少换酒店，本次南疆线继续这样安排吗？

用户可以：

沿用  
修改  
本次不用

所以：

### 每趟旅行拥有独立 Graph。

但是：

### 用户拥有跨 Graph 的可控 Memory。

这个架构现在就非常完整了。

# 九、Trip Agent Graph 正式成为整个产品的技术骨架

我建议以后主 PPT 不需要出现十几个 Agent 技术词。

重点只讲这个。

## **Trip Agent Graph**

至少有：

**Route**

路线与空间关系。

**Time**

时间窗口、ETA、固定时间点。

**Cost**

预算、实际成本、变更成本。

**Commitment**

酒店、订单、同行人约定。

**Constraint**

道路、预约、天气、驾驶偏好。

**Dynamic Fact**

不断变化的现实世界状态。

**Evidence**

每一个事实从哪里来。

**Action**

可以被执行的修改。

实际上可以理解成：

> **一个随着旅程进行不断变化、可被 Agent 推理和操作的旅行状态图。**

### MAINTAIN
更新 Graph + 传播变化 + Recovery。

### LEARN
总结 Graph + 产生候选 Memory。

这张图应该成为 PPT 的“核心技术总图”。
