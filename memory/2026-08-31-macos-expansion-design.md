# Design: Minis macOS 原生桌面版扩展方案

Generated by office-hours on 2026-08-31
Status: DRAFT
Mode: Startup（本轮仅讨论产品架构与工程落地，不讨论市场验证）

## 1. 决策摘要

Minis macOS 版采用以下组合，而不是整体复制 Codex 或 Grok Bot：

- **产品模型沿用当前 Minis：** 伙伴、群聊、成员私有会话、子 Agent、Skills、Memory、多 Provider。
- **桌面运行架构借鉴 Codex：** 富客户端与 Agent Runtime 分离，macOS 由独立 Runtime Service 承担会话执行、工具循环和长任务。
- **UI 技术继续使用 SwiftUI：** 新增原生 macOS Target，复用现有 SwiftUI 和 Swift 领域代码，不引入 Electron/React 作为第二套产品实现。
- **命令环境使用真实 macOS：** macOS 不运行 iSH/Alpine；非交互命令使用宿主进程，交互终端使用 PTY + 用户 shell。
- **分发采用 Developer ID 直签公证：** 首版不以 Mac App Store 为目标，不启用 App Sandbox；所有内嵌服务和辅助程序均启用 Hardened Runtime、签名并随外层发行物公证。

最终目标不是“同一个 Target”，而是：

> 一套 Agent Core、一套伙伴与群聊规则、一套数据契约，两套薄平台宿主。

## 2. 问题陈述

当前 iOS App 已经具备完整的端上 Agent Runtime，并围绕 iSH 建立了 Shell、文件挂载、Skills、MCP、原生 offload 与可见终端。近期增加的伙伴与群聊能力又直接建立在 `AIChatViewModel`、`ChatStore` 和会话体系之上。

macOS 扩展面临的核心问题不是重新开发聊天界面，而是：

1. 保证伙伴、群聊和 Agent Runtime 的行为与 iOS 同源。
2. 把 iSH/Alpine 替换为真实 macOS Shell，而不把平台差异扩散到上层业务。
3. 把当前兼具“Agent 引擎”和“UI ViewModel”职责的 `AIChatViewModel` 拆成可在独立进程运行的无界面 Runtime。
4. 让桌面端具备长任务、多个窗口、原生终端、真实项目目录和可靠进程管理能力。
5. 在非沙箱直签分发下，为 Agent 的本机执行建立明确、可见、可审计的安全边界。

## 3. 目标与非目标

### 3.1 V1 必须实现

- 使用现有 Provider、认证、Tool Loop、Skills、Memory 和 ChatStore 数据模型。
- 完整支持“会话 / 伙伴 / 群聊”三类入口。
- 保留伙伴的长期主会话、人格目录、默认模型和工具策略。
- 保留群聊的成员私有会话、`@id` 路由、串行发言、轮次上限、失败成员跳过和取消语义。
- 支持多个 Agent 会话并行运行，群聊内部仍严格串行。
- 使用真实 macOS Shell 执行 `shell_execute`。
- 提供基于 PTY 的交互终端，支持尺寸变化、信号、ANSI、复制粘贴和中文输入。
- 支持用户选择真实项目目录作为 workspace。
- 支持 Developer ID 签名、公证和可重复的发行构建。
- iOS 现有行为不得退化。

### 3.2 V1 明确不做

- 不把 iSH 或 Alpine 带到 macOS。
- 不追求 iOS 与 macOS 像素级一致。
- 不以 Electron/Grok Bot 桌面工程作为新主工程。
- 不替换当前 Agent Runtime 为 Codex App Server；只借鉴其客户端/Runtime 分离模式。
- 不要求 Agent 任务在用户明确退出 App 后继续运行。
- 不在首版支持任意远程客户端连接本机 Runtime。
- 不在首版实现强操作系统级命令沙箱；V1 使用工作区权限、审批、环境隔离和审计，后续再评估更强隔离。
- 不要求所有 iOS 原生 offload 在 Mac 上一一存在；按平台能力显式降级。

## 4. 已确认前提

1. 原生 macOS Target 是正式路线，Mac Catalyst 不作为最终架构。
2. Developer ID 直签公证优先于 Mac App Store。
3. Agent Runtime、伙伴和群聊是共享代码的最高优先级。
4. iOS 继续使用 iSH；macOS 使用宿主 Shell。
5. macOS 的 Agent 命令与用户可见终端是两个独立执行面。
6. “一套代码”意味着共享核心和协议，不意味着两个平台不能有少量专用 UI 与平台服务。

## 5. 当前代码复用判断

### 5.1 可直接共享或只需轻微调整

- `AgentKit/AgentProfile.swift`
- `AgentKit/Group/GroupProfile.swift`
- `AgentKit/Group/GroupMentionRouter.swift`
- `AgentKit/Group/GroupChatPrompt.swift`
- `AgentKit/OrchestratorPrompt.swift`
- `AgentKit/SubagentTools.swift`
- Provider 模型、请求构造、流式解析和配置模型
- ChatStore 的 SQLite Schema、会话关系和群聊表
- Tool 定义、参数校验和绝大多数工具结果模型
- Skills、Memory、SOUL 和 Flavor 契约
- 大部分 SwiftUI 表单、列表和设置状态

伙伴/群聊目录目前没有直接 `UIKit` import，领域模型和路由逻辑的跨平台条件很好。

### 5.2 需要改为 Runtime API 调用

- `AgentKit/Group/GroupChatOrchestrator.swift`
- `AgentKit/Group/GroupStore.swift`
- `AgentKit/SubagentCoordinator.swift`
- `AgentKit/AgentDirectoryCoordinator.swift`
- `AgentKit/AgentStore.swift`

这些模块的规则可以保留，但不能继续直接创建或查找 `AIChatViewModel`。它们应通过 `AgentSessionRunner`/`RuntimeClient` 创建会话、发送输入、等待结果、取消任务和订阅状态。

### 5.3 必须拆分的平台耦合

- `AIChatViewModel` 同时承担 Agent Loop、UI 状态、iOS 生命周期、触觉、图片和后台任务职责。
- `ISHExecutionCoordinator` 同时承担命令、路径解析、进程取消和 iSH 挂载职责。
- `AIChatViewModel+FileTools` 依赖 `/var/minis` 与 iSH 路径映射。
- `AIChatViewModel+BackgroundTask` 依赖 `UIApplication` 后台时间。
- 图片路径使用 `UIImage`，需要改为 Data/CGImage 为核心、平台图片为适配层。
- 当前终端 Canvas 与输入层使用 UIKit，需要 macOS 渲染与输入实现。

## 6. 最终总体架构

```text
┌──────────────────────────────────────────────────────────────┐
│                         Shared Domain                         │
│ AgentProfile · GroupProfile · Group Router · Prompts · Tools │
│ Providers · Skills · Memory · Chat Models · Persistence      │
└──────────────────────────────┬───────────────────────────────┘
                               │
                    Minis Runtime Protocol
            request / response / event / approval / stream
                               │
              ┌────────────────┴────────────────┐
              │                                 │
┌─────────────▼──────────────┐    ┌─────────────▼──────────────┐
│ iOS Direct Runtime         │    │ macOS Runtime Service      │
│ 与 App 同进程              │    │ 签名的独立辅助进程          │
│ iSH Command Backend        │    │ Host Command Backend       │
│ iSH TTY                    │    │ Process/POSIX + PTY        │
└─────────────┬──────────────┘    └─────────────┬──────────────┘
              │                                 │
┌─────────────▼──────────────┐    ┌─────────────▼──────────────┐
│ iOS SwiftUI/UIKit Shell    │    │ macOS SwiftUI/AppKit Shell │
│ Mobile navigation          │    │ Sidebar/Detail/Inspector   │
└────────────────────────────┘    └────────────────────────────┘
```

### 6.1 核心设计原则

- Runtime 是伙伴、群聊、任务和会话运行状态的唯一权威源。
- UI 不直接执行模型调用、Shell 或数据库写入。
- 数据库只能由一个 Runtime 实例写入，避免 UI 与服务进程竞争 SQLite。
- 平台能力通过协议注入，不在领域逻辑中散布 `#if os(...)`。
- 所有跨进程消息都带协议版本、请求 ID、会话 ID 和事件序号。
- iOS 和 macOS 运行同一套 Runtime 合同测试。

## 7. 模块设计

### 7.1 `MinisDomain`

职责：无 UI、无磁盘实现、无平台 API 的值类型和纯规则。

包含：

- `AgentProfile`
- `GroupProfile` / `GroupMember` / `GroupMessage`
- `GroupMentionRouter`
- `GroupChatPrompt`
- `GroupChatLimits`
- Tool schema 与参数验证
- Provider/Model 标识与通用配置值
- Runtime command/event 的 Codable 类型

约束：只依赖 Foundation；核心路由测试可脱离 App 编译。

### 7.2 `MinisAgentCore`

职责：真正的 Agent Runtime，不引用 SwiftUI、UIKit、AppKit。

主要对象：

- `AgentRunEngine`：单个会话的消息发送与 Tool Loop。
- `AgentSessionRunner`：创建、加载、发送、取消、等待会话。
- `AgentRuntime`：持有活动会话、并发槽位和事件总线。
- `ToolDispatcher`：调用 Shell、文件、浏览器、MCP、Native Tool。
- `ProviderRunner`：模型请求、流式响应、重试、OAuth 刷新协调。
- `ContextAssembler`：SOUL、Memory、Skills、附件和历史上下文。
- `RuntimeEventBus`：输出增量文本、思考、工具、状态和审批事件。

`AIChatViewModel` 最终退化为 Runtime 的 UI 客户端，不再是 Runtime 本身。

### 7.3 `MinisAgentKitCore`

职责：伙伴、群聊和子 Agent 的业务编排。

- `AgentStore` 与 `GroupStore` 保留 Observable 包装，但写入走 RuntimeClient。
- `GroupChatOrchestrator` 通过 `AgentSessionRunner` 驱动成员私有会话。
- `SubagentCoordinator` 通过同一 Runner 创建 executor 会话。
- `AgentDirectoryCoordinator` 不再访问 ViewModel Cache。
- 群聊的串行、轮次上限和 epoch 取消逻辑保持不变。

### 7.4 `MinisPersistence`

职责：ChatStore、迁移、索引、同步记录和事务。

- 沿用现有 `minis.db` Schema 和迁移链。
- macOS 使用独立本地数据库，不通过 iCloud Drive 直接同步 SQLite 文件。
- 跨设备同步继续走现有 Sync V2/CloudKit 记录层。
- Runtime Service 独占写连接；UI 通过 Runtime Protocol 查询。
- 群聊创建必须在一个事务语义中完成：群会话、群资料、成员关系。

### 7.5 `MinisPlatformContracts`

定义以下平台协议：

- `CommandExecutionBackend`
- `TerminalBackend`
- `WorkspaceResolver`
- `NativeToolHost`
- `CredentialStore`
- `AppLifecycleState`
- `NotificationHost`
- `ClipboardHost`
- `MediaCodecHost`
- `SystemOpenHost`

领域层和 AgentCore 只能依赖协议。

## 8. Runtime Protocol

### 8.1 传输

- iOS：`DirectRuntimeTransport`，同进程 actor 调用。
- macOS：`StdioRuntimeTransport`，主 App 启动签名的 `minis-runtime` 辅助可执行文件，通过双向 JSON 消息通信。
- 调试：可选本机 Unix Domain Socket，只允许 Debug Build。
- 首版不开放 TCP 监听。

选择 stdio 而不是直接把 XPC 类型暴露给业务层，原因是协议可以被测试、录制、回放，将来也能支持 CLI；macOS 进程监督仍可由主 App 或 XPC 包装承担。

### 8.2 消息信封

每条消息包含：

- `protocolVersion`
- `requestId`
- `method` 或 `event`
- `sessionId`/`agentId`/`groupId`（按需）
- `sequence`（流式事件）
- `payload`
- `error`

### 8.3 首版方法族

- Runtime：`initialize`、`capabilities`、`shutdown`、`snapshot`
- Session：`list`、`create`、`open`、`send`、`cancel`、`delete`
- Agent：`list`、`create`、`update`、`archive`、`openMainSession`
- Group：`list`、`create`、`update`、`send`、`cancel`、`openMemberSession`
- Tool：`approve`、`deny`、`cancel`
- Workspace：`grant`、`revoke`、`list`、`setSessionWorkspace`
- Terminal：`create`、`input`、`resize`、`signal`、`close`
- Provider：`list`、`test`、`setSessionBinding`

### 8.4 首版事件族

- `runtime.ready`
- `session.updated`
- `message.started` / `message.delta` / `message.completed`
- `thinking.delta`
- `tool.started` / `tool.output` / `tool.completed`
- `approval.requested` / `approval.resolved`
- `agent.activityChanged`
- `group.turnStarted` / `group.memberStarted` / `group.memberCompleted` / `group.completed`
- `terminal.output` / `terminal.exited`
- `runtime.warning` / `runtime.fatal`

事件序号允许 UI 发现丢包并请求 `snapshot` 重建状态。

## 9. macOS Runtime Service

### 9.1 生命周期

- 主 App 启动时检查 Runtime 版本并拉起服务。
- 同一 App 实例只允许一个 Runtime Service。
- Runtime 启动后打开数据库、恢复未完成会话状态、发布 `runtime.ready`。
- UI 窗口关闭不终止 Runtime；用户真正退出 App 时进行有期限的优雅关闭。
- 若 Runtime 崩溃，主 App最多自动重启一次并从数据库恢复；连续崩溃进入安全模式，不无限拉起。

### 9.2 进程职责

Runtime Service 负责：

- Provider 请求和 Tool Loop
- ChatStore 写入
- 伙伴、群聊与子 Agent 编排
- Shell 子进程和进程组
- MCP stdio server 生命周期
- Skills、Memory 和 workspace 文件工具
- 运行事件与审批状态

主 App 负责：

- SwiftUI/AppKit UI
- macOS 权限提示和 TCC 相关系统 API
- 文件选择、拖放和用户交互
- 通知、菜单、Dock、窗口
- Runtime 监督和更新提示

### 9.3 原生能力回调

Runtime 调用日历、通讯录、通知、照片等能力时，向主 App 发出反向 RPC：

`native.invoke(name, arguments, sessionId)`

主 App执行权限检查和系统 API，然后把结构化结果返回 Runtime。这样可以保留当前 `apple-calendar` 等命令契约，同时确保权限弹窗来自 GUI App。

## 10. macOS 命令执行

### 10.1 非交互式 `shell_execute`

实现 `MacCommandExecutionBackend`：

- 每次调用创建独立进程，不复用可见终端。
- 默认 shell 为 `/bin/zsh -l` 或用户配置的 shell。
- 命令脚本通过 stdin 传入，避免字符串二次转义。
- stdout/stderr 使用独立 pipe，统一按事件流输出。
- 为每个调用创建独立进程组，取消和超时杀死整个进程树。
- 每个会话拥有明确的 cwd、环境和 workspace ID。
- 支持同一会话及跨会话并发；群聊成员发言仍由编排层串行。
- 输出采用大小上限、尾部截断和二进制检测，避免无限内存增长。

### 10.2 环境变量

不直接把 GUI App 的完整环境继承给 Agent Shell。

基础白名单：

- `HOME`
- `USER`
- `SHELL`
- `PATH`
- `LANG` / `LC_*`
- `TERM`
- `TMPDIR`
- `MINIS_SESSION_ID`
- `MINIS_AGENT_ID`
- `MINIS_WORKSPACE`
- `MINIS_ATTACHMENTS`
- `MINIS_OFFLOADS`
- `MINIS_MEMORY`
- `MINIS_SKILLS`

Provider Token 不进入 Shell 环境。用户自定义变量继续由 EnvVarStore 管理，并在日志和工具结果中脱敏。

### 10.3 路径模型

macOS 不创建虚假的 `/var/minis`。共享提示词和 Skills 改用环境变量与能力描述。

默认内部目录：

```text
~/Library/Application Support/Minis/
  Database/
  Runtime/
  Sessions/<session-id>/
    workspace/
    attachments/
    offloads/
    browser/
  Agents/<agent-id>/
  Memory/
  Skills/
  Logs/
```

用户授权的项目目录作为 session workspace 记录，内部 session 目录仍保存附件和生成物元数据。

### 10.4 Shell 能力描述

系统提示词不再硬编码 Alpine、BusyBox 或 `apk`：

- iOS Runtime 宣告 `os=linux-guest`、`shell=ash`、`packageManager=apk`。
- macOS Runtime 宣告 `os=macos-host`、实际 shell、Homebrew 是否可用以及当前 workspace。
- Skill 可声明 `platforms: [ios-linux, macos-host]`。
- 不兼容 Skill 在加载前被解释为 unavailable，而不是运行后失败。

## 11. 原生交互终端

### 11.1 结构

- `MacTerminalSession` 使用 PTY 启动登录 shell。
- `TerminalBackend` 管理创建、输入、resize、signal、退出和 scrollback。
- Runtime Service 拥有 PTY master；UI 只收发终端事件。
- Agent `shell_execute` 不写入用户终端，避免输出和提示符互相污染。

### 11.2 UI 形态

首版提供两种入口：

1. 会话内底部终端面板，绑定当前 session workspace。
2. 独立“终端”窗口，支持多个 tab。

默认快捷键：

- `⌘J`：显示/隐藏当前会话终端
- `⌘⇧J`：新建独立终端
- `⌘K`：清屏（终端聚焦时）
- `⌘W`：关闭当前终端 tab，不退出 Runtime

### 11.3 终端渲染策略

第一选择：把现有 `ANSIParser`、`TerminalBuffer`、`TerminalEmulator` 中不依赖 UIKit 的部分抽为共享核心，新增 AppKit Canvas/Input 层。

在正式实现前做一个短周期技术验证，与成熟终端组件比较以下指标：

- Unicode 宽字符与组合字符
- 中文输入法
- 鼠标选择与复制
- ANSI/OSC 支持
- 大量输出性能
- resize 与全屏程序
- VoiceOver

若现有核心无法低风险满足这些指标，保持 `TerminalBackend` 不变，只替换渲染组件。

## 12. 伙伴和群聊的关键迁移

### 12.1 伙伴

伙伴的权威数据保持：

- `AgentProfile`
- 主会话 ID
- SOUL/persona 目录
- 默认模型绑定
- Tool Policy
- Memory/Skills 目录

`AgentStore.openMainSession` 改为调用 Runtime API，不再创建 Draft ViewModel。UI 订阅该伙伴主会话的状态和未读事件。

### 12.2 群聊

群聊仍然是“成员表 + 普通会话 transcript”，不创建第二套消息数据库。

必须保持的语义：

- 每个群成员有独立私有会话和上下文。
- 群 transcript 只投影成员最终发言，不泄漏工具过程和私有思考。
- `@id` 是稳定引用，展示名变化不破坏路由。
- 一个群同一时刻只有一个 orchestration loop。
- 用户中途追加消息进入下一轮窗口，不另起并发循环。
- 成员发言严格串行。
- 轮次、消息数和单成员超时上限保持。
- 单个成员失败按 pass 处理，不让整个群失败。

### 12.3 运行状态

新增共享状态模型：

- idle
- queued
- thinking
- runningTool
- waitingApproval
- speakingInGroup
- completed
- failed
- cancelled

群聊 UI 可显示“哪位伙伴正在处理”，但不改变编排顺序。

### 12.4 子 Agent 与群聊共享调度器

- 延续全局 `SessionConcurrencyManager` 槽位限制。
- 父 Agent 等待子 Agent 时保留其槽位的现有语义，首版不调整。
- 群聊成员执行与普通会话、子 Agent 使用同一调度器。
- Runtime 统一发布排队原因，桌面 UI 可以显示“等待执行槽位”。

## 13. macOS 产品界面

### 13.1 主窗口

采用原生三栏结构，但首版允许右栏折叠：

```text
┌────────────────┬──────────────────────────────┬──────────────────┐
│ 会话/伙伴/群聊 │ 当前聊天                      │ 上下文/成员/任务  │
│ 搜索与筛选     │ 消息、工具、附件、输入框      │ 文件、终端、状态  │
└────────────────┴──────────────────────────────┴──────────────────┘
```

- 左栏复用现有 `HomeTab` 的会话/伙伴/群聊信息架构。
- 中栏复用消息模型，但使用适合桌面的布局密度、选择和右键菜单。
- 右栏按场景显示伙伴资料、群成员、子任务、工作区文件或工具详情。

### 13.2 桌面交互

- 支持拖入文件和文件夹。
- 支持菜单栏命令和标准快捷键。
- 支持消息文本选择、右键复制、文件 Reveal in Finder。
- 工具执行详情使用 inspector 或可展开行，不使用全屏 cover。
- Settings 使用独立窗口。
- 终端可停靠或独立窗口。

### 13.3 多窗口范围

V1：一个主窗口 + 任意终端窗口。
V1.1：允许把一个会话或群聊单独打开为窗口。所有窗口连接同一 Runtime，不各自创建 Agent 实例。

## 14. 文件、同步与凭据

### 14.1 本地数据

- GUI App 与 Runtime Service 使用同一个 macOS App Group 容器进行 IPC 和内部数据共享。
- Runtime 是数据库唯一写者。
- 用户项目目录不复制到 App 容器；只保存授权、显示名和 workspace 元数据。

### 14.2 iOS/macOS 同步

- 使用与 iOS 相同的 CloudKit Container 和 Sync V2 记录格式。
- Developer ID 发行需要相应 provisioning profile 承载 CloudKit 等受限 entitlement。
- App Group 只解决同一台 Mac 上 GUI/Runtime/扩展共享，不承担跨设备同步。
- 同步前必须验证伙伴、群成员关系、隐藏 member session 和 subagent session 的完整性。

### 14.3 凭据

- Provider OAuth/API Key 继续存 Keychain。
- GUI 与 Runtime 使用同一 Keychain Access Group，或由 GUI 提供 `CredentialBroker` 反向 RPC；实现阶段优先选择攻击面更小、签名更容易验证的方案。
- 凭据不得写入 Runtime Protocol 日志、Shell 环境或 crash report。
- Runtime 日志统一走现有脱敏策略。

## 15. 平台能力矩阵

每个 Native Offload 必须声明：

- `available`
- `unavailable`
- `differentBehavior`
- `requiresPermission`

首版建议：

- Calendar/Contacts/Reminders/Open/Clipboard/Notifications：macOS 原生实现。
- Browser Use、Model Use、Sessions、Config：共享核心或 macOS 适配。
- Photos/Media/Speech/Location：按 macOS Framework 可用性实现并单独验收。
- HealthKit、NFC、HomeKit 等缺失或差异较大的能力：不向 macOS Agent 宣告，返回结构化 unavailable。
- FFmpeg：使用签名的内嵌可执行文件或 Framework，不依赖 iSH offload 拦截。

保持 CLI 名称兼容，但不保持内部实现兼容。

## 16. 安全设计

### 16.1 默认信任范围

macOS 直签版不启用 App Sandbox，但 Agent 默认仍采用“工作区写入”策略：

- 读取当前 workspace。
- 写入当前 workspace 和 Minis 内部 session 目录。
- 访问 workspace 外路径时请求审批。
- 网络访问遵循用户设置和 Tool Policy。
- 高风险命令在执行前显示命令、cwd、伙伴身份和影响范围。

交互终端是用户直接控制的 Shell，不套用 Agent Tool 审批；两者 UI 必须明确区分。

### 16.2 关键防护

- Runtime Protocol 不监听公网。
- Debug Unix Socket 使用随机会话 token，并默认关闭。
- 所有内嵌 executable 和 frameworks 单独签名。
- 不启用 JIT、关闭 Library Validation 等不必要 Hardened Runtime 例外。
- Shell 子进程使用最小环境变量集合。
- 终止命令时清理整个进程组。
- 对命令、文件写入、授权和 Native Tool 保留本地审计记录。
- 日志禁止记录 Provider Token、OAuth Refresh Token 和用户自定义 secret 值。

### 16.3 风险声明

V1 的工作区策略属于产品级权限和审批，不是强内核隔离。因为用户终端及宿主 Shell 本身可以访问用户权限范围内的数据，产品必须清楚区分：

- 用户亲自输入的终端命令；
- Agent 自动执行、已审批执行和被拒绝执行的命令。

## 17. 构建、签名、公证与更新

### 17.1 Targets

- 现有 iOS Targets：保持。
- `MinisMac`：原生 macOS GUI App。
- `MinisRuntimeService`：无 UI 辅助可执行文件。
- 可选 `MinisMacTests` 与 `MinisRuntimeContractTests`。

### 17.2 签名顺序

1. 签名第三方 CLI/Framework。
2. 签名 `MinisRuntimeService`。
3. 签名 XPC/扩展（如有）。
4. 签名 `MinisMac.app`。
5. 生成 DMG 或 ZIP。
6. 上传公证。
7. staple ticket。
8. 在干净用户账户验证 Gatekeeper、权限和 Shell。

所有 executable 启用 Hardened Runtime。CloudKit 等高级能力使用 Developer ID provisioning profile。

### 17.3 更新

首版采用独立稳定/测试更新通道。更新系统必须验证签名，并能一起替换 GUI 与 Runtime Service，禁止只升级其中一个导致协议不兼容。

## 19. 分阶段交付计划

### Phase 0：契约与基线（约 1 周）

- 固化 iOS 当前 Agent、伙伴、群聊回归测试。
- 定义 Runtime Protocol 和 Platform Contracts。
- 建立平台能力矩阵。
- 记录当前关键流程的结构化 trace 作为 parity 基线。

退出条件：不改变产品行为，协议和测试边界经评审确认。

### Phase 1：拆出 Headless Agent Core（约 2–4 周）

- 从 `AIChatViewModel` 提取 `AgentRunEngine`。
- ViewModel 改为 Runtime 事件的 presentation adapter。
- Group/Subagent/AgentDirectory 改用 `AgentSessionRunner`。
- iOS 继续使用 DirectRuntimeTransport。

退出条件：iOS 所有现有功能和群聊测试通过；核心模块不再 import UIKit/SwiftUI。

### Phase 2：macOS 最小产品壳（约 2–3 周）

- 新增原生 macOS Target。
- 接入 ChatStore、Providers、AgentList、GroupList 和基础聊天。
- Runtime 暂可先同进程运行，使用 mock/受限 MacCommandBackend。
- 完成三栏主窗口和文件拖入。

退出条件：可以创建伙伴、创建群聊、发送群消息并正确串行回复。

### Phase 3：真实 Shell 与 Workspace（约 2–3 周）

- 实现 MacCommandExecutionBackend。
- 接入真实项目目录、路径变量、命令审批和进程组取消。
- 迁移 MCP stdio。
- 删除 macOS 提示词中的 Alpine 假设。

退出条件：普通会话、伙伴和群成员均可在各自 workspace 使用 shell/file 工具。

### Phase 4：独立 Runtime Service（约 2–4 周）

- 将 macOS Runtime 从进程内切换到 StdioRuntimeTransport。
- Runtime 独占数据库并输出可恢复事件。
- 实现崩溃重启、snapshot resync 和版本握手。
- 接入 Keychain/NativeTool 反向 RPC。

退出条件：关闭重开窗口不终止任务；Runtime 崩溃能恢复 UI 和已落盘状态。

### Phase 5：原生终端与桌面完成度（约 2–3 周）

- PTY TerminalBackend。
- 会话内终端面板、独立窗口和多 tab。
- 菜单、快捷键、右键菜单、Finder 联动。
- 性能和辅助功能验证。

退出条件：交互 Shell、全屏终端程序、中文输入、resize 和信号行为稳定。

### Phase 6：同步、签名与发行（约 2 周）

- CloudKit/Sync V2 跨设备测试。
- 完整 Developer ID 签名和公证流水线。
- 自动更新通道。
- 干净机器、升级安装和回滚测试。

退出条件：可重复生成通过 Gatekeeper 的发行包，iOS/macOS 数据可安全同步。

估算合计：一个熟悉当前代码的核心开发者约 11–17 周；两名开发者可并行 UI/平台与 Runtime，但 Phase 1 是关键串行路径。

## 21. 成功标准

- iOS 与 macOS 使用同一个 `AgentRunEngine`、伙伴模型和群聊编排代码。
- 不存在 macOS 专用的第二套伙伴/群聊业务实现。
- 现有 GroupChatRoutingTests 在共享 Core 上原样通过。
- macOS 能同时运行至少 5 个普通/伙伴会话；群聊内部仍严格串行。
- `shell_execute` 与交互终端互不污染、可独立取消。
- Runtime Service 重启后 UI 能通过 snapshot 恢复已落盘状态。
- 主流程源码共享率以 Target 编译文件统计达到至少 75%，而不是以界面像素复用率衡量。
- iOS 的启动、聊天、Shell、伙伴和群聊无功能回归。
- 发行包在干净 macOS 账户通过 Gatekeeper、权限和更新验证。

## 22. 主要风险与缓解

### 风险 1：`AIChatViewModel` 拆分范围过大

缓解：先引入接口并转发到原实现，再逐段把 Provider、Tool Loop、Persistence 移入 Engine；每一步保持 iOS 可运行。

### 风险 2：把 Runtime 进程化和 macOS UI 同时推进导致调试困难

缓解：macOS 首先使用 DirectRuntimeTransport 跑通产品，再切 StdioRuntimeTransport；两个 Transport 必须共享合同测试。

### 风险 3：Skills 和提示词默认假设 Alpine

缓解：启动时注入结构化 `RuntimeCapabilities`，建立 Skill 平台声明，禁止上层拼接固定 `/var/minis`。

### 风险 4：非沙箱 Agent 权限过大

缓解：默认 workspace-write、路径外审批、最小环境、命令审计、明确区分用户终端与 Agent 自动执行。

### 风险 5：macOS 原生能力与 iOS 不完全对称

缓解：能力发现优先；不可用能力不进入 Tool 定义和系统提示词，不做假兼容。

### 风险 6：CloudKit 与 Helper entitlement 复杂

缓解：发行前单独建立签名矩阵测试；同机 IPC 用 App Group，跨设备只走 Sync V2，不共享数据库文件。

## 24. 开放问题与建议默认值

1. **App 退出后任务是否继续？** 默认否；窗口关闭可继续，明确 Quit 则停止。
2. **默认 Shell？** 使用用户登录 shell；无法识别时回退 `/bin/zsh`。
3. **默认权限？** Agent 为 workspace-write；用户终端为用户直接控制。
4. **V1 是否包含 iCloud 同步？** 建议包含，但排在本机伙伴/群聊和 Runtime 稳定之后。
5. **最低 macOS？** 建议 macOS 14。
6. **是否首版多聊天窗口？** 默认不做，仅主窗口 + 终端窗口。
7. **终端组件自研还是引入成熟实现？** 由 Phase 0 技术验证决定，后端协议不受影响。

## 27. What I noticed

用户连续强调“尽可能用一套代码实现两种产品形态”，并进一步明确“最大的目的是复用当前的 Agent Runtime 以及伙伴和群聊”。这使架构选择从“最快做出一个 Mac UI”转向“先保护产品内核”。当前伙伴和群聊代码已经把 Grok Bot 中最有价值的社交 Agent 模型移植到了 Swift；再采用 Grok Bot 的 Electron 工程会重新制造一套 Runtime。相反，Codex 式客户端/Runtime 分离恰好能把现有 Swift Runtime 提升为两个平台共同使用的核心，同时允许 iOS 保留 iSH、macOS 使用真实宿主终端。
